# Session-authenticated real-time foundation

DigiStream exposes one authenticated WebSocket endpoint:

```text
GET /api/v1/realtime
Sec-WebSocket-Protocol: digistream.realtime.v1
Cookie: digistream_session=<opaque session token>
```

A normal HTTP request to this path returns `426 Upgrade Required`. The upgrade succeeds only when the existing opaque session is active, unexpired, unrevoked and belongs to an active user.

## Connection lifecycle

Every accepted connection receives a unique connection ID. Multiple browser tabs may connect with the same account, but each tab is represented independently.

The first server event is:

```json
{
  "type": "realtime.connected",
  "connectionId": "uuid",
  "user": {
    "id": "uuid",
    "displayName": "Example user"
  },
  "rooms": [
    {
      "key": "user:<user-id>",
      "kind": "user",
      "id": "<user-id>"
    }
  ],
  "protocol": "digistream.realtime.v1",
  "heartbeatIntervalMs": 30000
}
```

The authenticated user room is joined automatically and cannot be left. It will later carry durable notification wake-ups; it does not replace persisted notification records.

The server sends WebSocket ping frames and terminates clients that stop answering. Active sessions are rechecked periodically, so revoked or expired sessions are disconnected. Reconnecting always performs the complete cookie-session authorization again.

## Client commands

Clients send bounded JSON text messages. Binary frames and WebSocket extensions are rejected.

Application ping:

```json
{
  "type": "ping",
  "requestId": "optional-client-id"
}
```

Join an organisation room:

```json
{
  "type": "join",
  "requestId": "optional-client-id",
  "room": {
    "kind": "organisation",
    "id": "organisation-uuid"
  }
}
```

Join a broadcast room:

```json
{
  "type": "join",
  "requestId": "optional-client-id",
  "room": {
    "kind": "broadcast",
    "id": "broadcast-uuid",
    "organisationId": "organisation-uuid"
  }
}
```

Use the same room object with `"type": "leave"` to leave organisation and broadcast rooms.

### Reactions

A client must first join an authorized broadcast room. Reactions are ephemeral audience interaction, not listener-count or analytics evidence.

```json
{
  "type": "reaction.send",
  "requestId": "client-reaction-id",
  "room": {
    "kind": "broadcast",
    "id": "broadcast-uuid",
    "organisationId": "organisation-uuid"
  },
  "reaction": "👍"
}
```

The server accepts only the bounded set `👍`, `❤️`, `👏`, `😂`, `🔥`, and `🎉`. The default reaction budget is eight per connection per ten seconds. Exceeding that budget returns `REALTIME_REACTION_RATE_LIMITED` with a bounded `retryAfterMs`; it does not create a reaction event and does not disconnect an otherwise healthy client.

Authorized room members receive `reaction.sent` with the server-authoritative user ID and timestamp. Clients cannot supply actor identity or arbitrary room keys.

### Typing state

Typing is also limited to a broadcast room the current connection has already joined:

```json
{
  "type": "typing.set",
  "requestId": "typing-id",
  "room": {
    "kind": "broadcast",
    "id": "broadcast-uuid",
    "organisationId": "organisation-uuid"
  },
  "active": true
}
```

`typing.changed` is transient state. An active signal expires automatically after five seconds by default. Re-sending `active: true` refreshes that connection's timer; `active: false`, leaving the room, or ending the socket clears it early. This prevents stale “is typing” UI after a dropped tab or reconnect.

Typing state is per connection, deliberately. Two tabs from the same account can therefore have independent timers, and closing one tab cannot silently keep that tab's typing state alive.

## Authorization rules

Room keys are generated by the server. A client cannot submit an arbitrary string room name.

- `user:<id>` — only the authenticated user's own ID.
- `organisation:<id>` — only current organisation members.
- `broadcast:<id>` — the channel must be active and the broadcast must be scheduled, starting, live, reconnecting or ending.
- Public and unlisted broadcast rooms may be joined by any authenticated active user who knows the broadcast ID.
- Private broadcast rooms require current membership in the owning organisation.
- Failed authorization uses one generic room-unavailable response to avoid exposing private tenant existence.
- Reactions and typing additionally require that the specific socket has already joined the authorized broadcast room.

## Defensive limits

The foundation includes:

- Origin allow-listing using `REALTIME_ALLOWED_ORIGINS` or `WEB_ORIGIN`.
- A required versioned subprotocol.
- Mask enforcement for browser-to-server frames.
- Strict UTF-8 text decoding.
- A 16 KiB default message limit.
- No per-message compression or negotiated extensions.
- Per-connection command-rate limits.
- Separate reaction-rate limits.
- Expiring per-connection typing state.
- Per-user connection limits while still supporting multiple tabs.
- Socket backpressure limits.
- Heartbeat cleanup and periodic session revalidation.
- Graceful close during Fastify shutdown.

Production must configure an explicit web origin. Missing Origin headers are rejected in production unless `REALTIME_ALLOW_MISSING_ORIGIN=true` is deliberately set for a trusted non-browser client.

## Current boundary

The real-time owner provides connection authentication, room authorization, lifecycle management, bounded reactions and expiring typing events. Durable chat remains owned by the existing chat API and PostgreSQL; transient WebSocket events do not replace durable chat history.

User-visible presence, moderation controls and durable notifications remain separate roadmap work. In particular, socket presence must never be presented as media listener counts, and notification delivery must never precede persistence.

The hub is currently process-local. That is correct for the single API instance used by development and the current smoke stack. Before horizontally scaling the API, room fan-out, interaction throttling and presence coordination must move behind Redis while PostgreSQL remains the source of truth for durable chat and notifications.
